# Report And Result

用于 `automations/review/quality/INSTRUCTION.md` 的报告、结果落盘、提交和推送阶段。

## 固定输出格式

1. 审查范围
   - 昨日时间窗口（UTC+8 绝对时间）
   - 被审查的提交列表（hash + message + author）

2. 一份好代码应该是什么样
   - 用自己的话简洁总结本次采用的质量标准，不要原样照抄规则文本。

3. 评分方法
   - 100 分制
   - 5 个维度分值
   - 高/中/低严重度如何扣分
   - 体量与复杂度阈值

4. 总分
   - 给出 0-100 的总分
   - 给出一句总体判断：优秀 / 良好 / 一般 / 较差

5. 分项评分
   - 每个维度的得分、扣分原因、涉及提交/文件

6. 主要问题清单
   - 按严重程度排序：高 / 中 / 低
   - 每条都包含：提交 hash、文件路径、尽量精确到行号或函数/组件名、问题描述、为什么这是代码质量问题、优化建议

7. 正向观察
   - 写出结构、命名、拆分、边界控制上做得好的点

8. Review 建议
   - 给出一个简洁的人工 review 清单，告诉用户今天最值得重点盯的质量问题类型

9. 自动修复与 PR
   - 仅在触发低分自动修复时输出。如果未触发，写明未触发原因。

10. 结果文件
    - 写明本次 Markdown 结果文件路径。

11. 结果提交与推送
    - 写明结果文件提交 hash、推送目标分支，以及 PR URL（如适用）。

## 结果落盘

每次执行都必须把最终中文报告写入 `automations/review/quality/result/YYYY-MM/` 月份目录：

- 如果目录不存在，先创建目录。
- 结果文件必须是 Markdown 文件，扩展名为 `.md`。
- 文件名必须包含北京时间月日和本次总分，格式为：
  `MM-DD_score-<score>_RESULT.md`
- 时间使用 UTC+8（Asia/Shanghai）执行完成时间，不使用 UTC 时间。
- `<score>` 使用 0-100 的整数分数；如果昨日 main 无新增提交、没有产生分数，则使用 `no-commits`。
- 写入内容必须与最终输出给用户的报告一致；如果触发自动修复与 PR，文件中也必须包含“自动修复与 PR”小节和 PR URL/失败原因。
- 在最终回复和报告第 10 节都必须给出该结果文件路径。
- 不要把结果写到 `$CODEX_HOME` 或临时目录；这个目录用于纳入 git 版本管理。

## 结果提交与推送

每次执行结束后，不管是否触发自动修复，都必须把本次结果推送到远端，让用户可以从 GitHub 看到执行结果。

### 不触发自动修复时

适用场景：昨日无业务/代码提交，或总分大于等于 90。

- 只提交本次新增的 `automations/review/quality/result/YYYY-MM/*.md` 结果文件；不要把无关工作树改动一起提交。
- 在当前 `main` 上提交结果文件，提交信息使用：
  `docs: add code quality review result YYYY-MM-DD score <score>`
- 如果没有分数，提交信息使用：
  `docs: add code quality review result YYYY-MM-DD no commits`
- 提交后必须 `git push origin main`。
- 如果 push 失败，必须在最终回复和结果文件中写明失败原因、结果提交 hash、可手动重试的 push 命令。

### 触发自动修复时

- 结果文件必须包含在修复分支提交或同一修复 PR 的后续提交中，并随修复分支一起推送到 `origin`。
- PR 创建成功时，最终回复和结果文件必须写明 PR URL；用户主要通过该 PR 审查修复和当日报告。
- 如果修复失败或 PR 创建失败，仍必须尽量提交并推送结果文件所在分支；最终回复必须写明分支名、提交 hash、失败原因和可手动重试命令。

## 防止结果提交污染次日评分

- 下一次运行筛选昨日提交时，必须排除只修改 `automations/review/quality/result/` 月份目录下结果文件的结果提交。
- 历史上的 `automations/code/result/` 结果提交也应继续排除。
- 如果一个提交同时包含结果文件和真实代码变更，则不能排除；只按真实代码变更部分进行质量审查。
