# Atmos Main 每日代码质量评分

在当前工作区仓库中，只审查 `main` 分支前一天产生的所有提交。时间范围以 UTC+8（Asia/Shanghai）自然日为准，即昨天 `00:00:00` 到 `23:59:59`。

先确认并同步 `main` 的最新状态，然后基于该时间窗口内 `main` 分支上的提交做审查。如果昨天没有业务/代码提交，明确写出“昨日 main 无新增提交”，不要修复，不要创建 PR，但仍必须按“结果落盘”和“结果提交与推送”规则写入并推送结果文件。

报告语言：中文。

隐私与路径约束：
- 审查过程与结果文件不得包含本机绝对路径（例如 `/Users/...`、`C:\\...` 等本地环境路径），避免泄露开发者机器目录信息。
- 文件路径应使用仓库内路径表达，例如 `apps/...`、`crates/...`、`automations/code/result/...`；只在仓库根已知上下文中使用。
- 若需给出“完整路径”，优先使用仓库内统一的相对路径格式，不使用运行机器的绝对路径前缀。

## 目标边界

- 这不是功能验收，也不是产品/需求 review。
- 不评价“需求是否合理”或“功能是否符合产品预期”。
- 只评价代码质量与设计质量，帮助人工 review。
- 只看“本次提交引入、放大或改善了什么质量问题”，不要把仓库历史遗留问题直接算到当天提交头上，除非该提交明显延续、复制、扩大了这些问题。
- 审查提交列表时，忽略 automation 自己生成的结果文件提交，例如只改动 `automations/code/result/` 的提交，或提交信息形如 `docs: add code quality review result ...` 的提交。这类提交只用于结果归档，不应参与当天代码质量评分。

## 一份好代码应该是什么样

请先用自己的话解释本次采用的质量标准，再按标准评分。不要临时改变评分口径，也不要机械照抄规则文本。

1. 职责单一且边界清晰
   - 文件、模块、组件、函数应围绕一个清晰职责展开。
   - 好代码应让人快速回答“这段代码归谁负责、为了什么存在、为什么在这一层”。
   - 如果一个文件同时混合业务规则、IO、UI 拼装、状态协调、数据转换，属于质量下降信号。

2. 分层方向正确，不跨层偷跑
   - 底层不应反向依赖上层；公共层不应夹带业务细节；UI/handler 不应承载大段业务规则。
   - 新增代码应沿既有架构层次流动，而不是绕过边界直接操作不该接触的对象。

3. 抽象贴合当前问题，不过度也不欠缺
   - 好抽象能消除重复、稳定边界、降低理解成本。
   - 为一次性场景引入复杂框架、泛型、配置层、trait/interface 层，属于过度设计。
   - 明明已有重复逻辑却继续复制粘贴，属于欠设计。

4. 可读性优先，控制流易追踪
   - 阅读时应能顺着主路径理解行为，不需要在多个状态位、嵌套分支、隐式副作用之间来回跳转。
   - 好代码会把复杂度切开，而不是把所有分支塞进一个超长函数或组件。

5. 命名和接口表达准确
   - 变量、函数、类型、组件、文件名应准确表达意图和边界。
   - 参数、返回值、字段、事件名应减少歧义，让调用者不必猜测语义。

6. 体量受控，规模与职责匹配
   - 代码可以因为问题复杂而变长，但长度必须换来清晰结构。
   - 真正的问题是“体量过大且职责混杂、阅读成本失控、拆分点明显却未拆”。

7. 复用合理，避免重复和隐式约定
   - 相同规则、映射、拼装逻辑不应在多个地方各写一份。
   - 常量、策略、规则、schema、事件名、魔法字符串不应靠口口相传维持一致。

8. 工程卫生稳定
   - 不应留下调试日志、临时开关、注释掉的旧代码、无解释的魔法值、一次性 patch、顺手修但未收口的痕迹。
   - 错误处理、边界处理、日志信息应体现稳定工程习惯。

9. 改动对未来维护者友好
   - 后续开发者应能低成本定位修改点、替换实现、补测试、排查问题。
   - 如果本次提交让未来改动更难、更脆、更依赖上下文记忆，应扣分。

10. 测试代码也要讲设计质量
   - 如果提交修改了测试，只评价测试代码是否清晰、稳定、低耦合、低脆弱性。
   - 不因为“测到了很多”加分；也不评价业务覆盖率是否足够。

## 固定评分方法

总分 100 分，固定权重如下：

- 设计与分层：30 分。看职责边界、模块耦合、分层方向、抽象是否贴合。
- 可读性与复杂度：25 分。看控制流、状态管理、分支复杂度、理解成本。
- 体量与内聚：20 分。看文件/函数/组件是否过大且混杂，拆分点是否明显。
- 可维护性与复用：15 分。看重复代码、共享逻辑组织、配置/常量/协议是否集中管理。
- 工程卫生：10 分。看命名、注释、错误处理、日志、调试残留、临时性实现痕迹。

严重度扣分规则：

- 高严重度问题：单项通常扣 8-15 分。例如明显分层穿透、超大文件/组件承载多个职责、关键控制流极难理解、复制粘贴核心逻辑导致未来易分叉、提交引入明显难维护结构。
- 中严重度问题：单项通常扣 3-7 分。例如命名含混、局部抽象不稳、函数过长但仍可理解、参数过多、中等规模重复、边界处理不完整、测试结构脆弱。
- 低严重度问题：单项通常扣 1-2 分。例如少量魔法值、小范围调试残留、注释与实现轻微脱节、局部文件组织一般但未明显伤害结构。
- 同一问题不要重复扣分；只有确实造成额外后果时才在其他维度少量扣分并说明原因。
- 不因风格偏好扣分，不因复杂业务天然扣分，不把历史债务直接算给当天提交。

体量与复杂度阈值是 review 信号，不是机械死规则。只有当阈值超出且结构也变差时才作为明确问题提出：

- 单文件：300 行以内通常安全；300-500 行需关注职责；500-800 行通常是中风险；800 行以上通常是高风险，生成文件、schema、常量表、纯类型映射等天然大文件除外。
- 单函数/方法：40 行以内通常可接受；40-80 行需检查是否含多个阶段；80-150 行通常是中风险；150 行以上通常是高风险。
- 单 UI 组件：150 行以内通常可接受；150-250 行需检查是否混合数据获取、状态编排、视图渲染、交互副作用；250-400 行通常是中风险；400 行以上通常是高风险。
- 参数数量：5 个以上需要检查接口是否泄漏实现细节；8 个以上通常是中风险。
- 嵌套和状态复杂度：3 层以上嵌套分支、多个布尔状态交叉驱动、依赖隐式时序的副作用，通常视为复杂度风险。

## 审查原则

1. 先看提交 diff，再看必要上下文，不要脱离改动范围泛泛点评整个仓库。
2. 所有问题尽量落到具体证据：提交 hash、文件路径、函数/组件名、必要时给行号。
3. 如果证据不足，只能写“推测”，不能当成事实。
4. 不要凑问题数量；如果当天质量很好，就明确写“未发现明确质量问题”。
5. 除了指出问题，也要写出正向观察，帮助形成稳定 review 标尺。
6. 每条问题下面都必须给出“优化建议”，而且必须可落地。
7. 优化建议不能只写“考虑重构”“建议优化”“适当拆分”。必须说明怎么落地，例如抽哪段逻辑、把哪类状态下沉到哪个模块、把哪组常量集中到哪里、把哪两个职责拆开、把哪类重复逻辑收敛成什么接口。

## 固定输出格式

1. 审查范围
   - 昨日时间窗口（UTC+8 绝对时间）
   - 被审查的提交列表（hash + message + author）

2. 一份好代码应该是什么样
   - 用自己的话简洁总结本次采用的质量标准，不要原样照抄规则文本。

3. 评分方法
   - 100 分制
   - 5 个维度分值
   - 高/中/低严重度如何扣分
   - 体量与复杂度阈值

4. 总分
   - 给出 0-100 的总分
   - 给出一句总体判断：优秀 / 良好 / 一般 / 较差

5. 分项评分
   - 每个维度的得分、扣分原因、涉及提交/文件

6. 主要问题清单
   - 按严重程度排序：高 / 中 / 低
   - 每条都包含：提交 hash、文件路径、尽量精确到行号或函数/组件名、问题描述、为什么这是代码质量问题、优化建议

7. 正向观察
   - 写出结构、命名、拆分、边界控制上做得好的点

8. Review 建议
   - 给出一个简洁的人工 review 清单，告诉用户今天最值得重点盯的质量问题类型

9. 自动修复与 PR
   - 仅在触发低分自动修复时输出。如果未触发，写明未触发原因。

10. 结果文件
    - 写明本次 Markdown 结果文件路径。

11. 结果提交与推送
    - 写明结果文件提交 hash、推送目标分支，以及 PR URL（如适用）。

## 总分解释口径

- 90-100：优秀，结构清晰，只有轻微问题或几乎无问题。
- 75-89：良好，整体设计合理，但存在值得尽快修正的局部质量问题。
- 60-74：一般，可工作，但已有明显维护成本或结构风险。
- 0-59：较差，结构问题明显，建议在继续迭代前先治理质量。

## 低分自动修复与 PR 创建

本节是条件执行规则，必须在完成代码质量评分后执行。

### 触发条件

- 如果昨日 main 无业务/代码提交：输出“昨日 main 无新增提交”，不要修复，不要创建 PR，但仍按结果落盘和结果提交与推送规则提交并推送结果文件。
- 如果总分 >= 90：只输出审查报告，不要修改代码，不要创建 PR。
- 如果总分 < 90：必须自动进入修复流程；不要询问用户是否修复。

### 修复边界

- 只修复本次审查确认由昨日 main 提交引入、放大或固化的代码质量/设计质量问题。
- 不做功能验收，不改变产品需求，不扩展未要求的新功能。
- 优先修复导致扣分的高/中严重度问题；低严重度问题只有在同一改动范围内顺手收口且风险很低时才处理。
- 按仓库现有架构和 AGENTS.md 指引做最优设计：职责拆分、分层回正、重复逻辑收敛、控制流简化、命名和接口收口。
- 不要为了“修复”引入一次性复杂框架或大范围无关重构。
- 如果工作树存在本次 automation 之外的未提交改动，不要覆盖或回滚。优先使用独立分支/工作树隔离修复；如果无法安全隔离，报告阻塞原因，不要破坏用户改动。

### 分支、提交和验证

- 在同步后的 main 基础上创建独立修复分支，建议命名为 `codex/quality-fix/YYYY-MM-DD`；如果分支已存在，追加短时间戳或短 hash 保证唯一。
- 完成修复后运行与改动相关的最小可靠验证，例如 `cargo fmt`、目标 `cargo test`/`cargo check`、`bun --filter web typecheck`、针对改动文件的 lint、`git diff --check`。
- 如果全仓库检查因无关历史问题失败，必须说明失败文件与本次改动是否相关，并补跑针对本次改动的验证。
- 使用 conventional commit 提交修复，提交信息应反映质量修复主题，例如 `refactor: improve daily quality findings`。
- 不要把审查报告之外的无关改动放进同一个提交。

### 创建 PR

- 修复提交完成后，必须推送修复分支到 `origin`，然后使用本地 `gh` CLI 创建 PR，base 必须是 `main`。
- 必须优先使用仓库 PR 模板 `.github/PULL_REQUEST_TEMPLATE.md` 填写 PR body；如果模板缺失，使用同等结构：Summary、Related Issue、Type of Change、Validation、Checklist。
- PR 标题应包含质量修复语义和审查日期，例如 `refactor: address daily quality findings for YYYY-MM-DD`。
- PR body 必须包含：原始质量评分、触发修复的主要问题、修复摘要、验证命令与结果、剩余风险或未处理原因。
- 如果仓库存在 `codex` 和 `codex-automation` labels，创建 PR 后必须添加这两个标签；如果任一 label 不存在，说明跳过原因，不要因为 label 缺失阻塞 PR。
- 如果 `gh pr create` 因认证、网络或权限失败，必须保留本地分支和提交，输出失败原因、分支名、提交 hash，以及可手动重试的 `gh pr create` 命令。

### 输出要求补充

- 如果总分 < 90 且 PR 创建成功，必须给出：修复分支、提交 hash、PR URL、验证摘要、人工 review 最应关注的剩余风险。
- 如果总分 < 90 但未能创建 PR，必须明确写出阻塞点和下一步人工操作。
- 用户每天只审查 PR，因此低分场景不要停留在报告层面；必须尽最大可能交付可 review 的 PR。

## 结果落盘

每次执行都必须把最终中文报告写入本文件同级目录下的 `result/` 目录：

- 目录固定为 `automations/code/result/`。
- 如果目录不存在，先创建目录。
- 结果文件必须是 Markdown 文件，扩展名为 `.md`。
- 文件名必须包含北京时间执行时间和本次总分，格式为：
  `YYYY-MM-DD_HH-mm-ss_score-<score>_ATMOS_CODE_QUALITY_REVIEW.md`
- 时间使用 UTC+8（Asia/Shanghai）执行完成时间，不使用 UTC 时间。
- `<score>` 使用 0-100 的整数分数；如果昨日 main 无新增提交、没有产生分数，则使用 `score-no-commits`。
- 写入内容必须与最终输出给用户的报告一致；如果触发自动修复与 PR，文件中也必须包含“自动修复与 PR”小节和 PR URL/失败原因。
- 在最终回复和报告第 10 节都必须给出该结果文件的完整路径。
- 不要把结果写到 `$CODEX_HOME` 或临时目录；这个目录用于纳入 git 版本管理。

## 结果提交与推送

每次执行结束后，不管是否触发自动修复，都必须把本次结果推送到远端，让用户可以从 GitHub 看到执行结果。

### 不触发自动修复时

- 适用场景：昨日无业务/代码提交，或总分 >= 90。
- 只提交本次新增的 `automations/code/result/*.md` 结果文件；不要把无关工作树改动一起提交。
- 在当前 `main` 上提交结果文件，提交信息使用：
  `docs: add code quality review result YYYY-MM-DD score <score>`
- 如果没有分数，提交信息使用：
  `docs: add code quality review result YYYY-MM-DD no commits`
- 提交后必须 `git push origin main`。
- 如果 push 失败，必须在最终回复和结果文件中写明失败原因、结果提交 hash、可手动重试的 push 命令。

### 触发自动修复时

- 结果文件必须包含在修复分支提交或同一修复 PR 的后续提交中，并随修复分支一起推送到 `origin`。
- PR 创建成功时，最终回复和结果文件必须写明 PR URL；用户主要通过该 PR 审查修复和当日报告。
- 如果修复失败或 PR 创建失败，仍必须尽量提交并推送结果文件所在分支；最终回复必须写明分支名、提交 hash、失败原因和可手动重试命令。

### 防止结果提交污染次日评分

- 下一次运行筛选昨日提交时，必须排除只修改 `automations/code/result/` 的结果提交。
- 如果一个提交同时包含结果文件和真实代码变更，则不能排除；只按真实代码变更部分进行质量审查。
