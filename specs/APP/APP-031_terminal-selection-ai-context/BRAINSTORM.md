# Brainstorm · APP-031: Terminal Selection AI Context

> Problem space and exploration. Settled content graduates to PRD.md; committed architecture graduates to TECH.md.

## Context

Terminal AI Input already supports side chats from terminal context, but the source context is currently implicit: `/side` captures a bounded pane transcript. Users can now select terminal text directly, which creates a better intent signal. A selected range should be attachable as explicit AI Input context, and side chat should be able to start from that exact range.

There is also a command parsing bug: copied or pasted text that contains `/side` can activate side-chat mode even when the user only meant to send that text. The command should be activated by a structured chip, not by plain text.

## Goals (draft)

- Let users convert a terminal text selection into a visible `Selection` AI Input context chip.
- Let users start a side chat from the selected text with one toolbar action.
- Make prompt construction explicitly say the context came from a user-selected terminal range.
- Stop treating raw `/side` text as command activation.
- Reuse the existing Appshot-style protocol token pattern for structured composer chips.

## Options

### Option A - Selection chip plus side-mode chip

When text is selected in the terminal, a small toolbar appears with:

- `Add as context`, using `MessageCircleMore`.
- `Side chat for selection`, using `MessageCirclePlus`.

`Add as context` inserts a `Selection` chip. `Side chat for selection` inserts the same `Selection` context and also activates a side-chat chip. The side chip serializes as `atmos://side-chat/{context_id}`.

**Pros**: Most explicit. Selection and side mode remain separate concepts. Users can remove the side mode and keep the selection context, or remove the selection context before submitting.
**Cons**: The UI may show two chips for one toolbar action unless the visual design groups them carefully.
**Unknown**: Whether the side chip should be displayed as `Side` or folded into the `Selection` chip state.

### Option B - One combined `Side Selection` chip

`Side chat for selection` inserts one chip that both identifies the selected text and turns on side mode. The serialized token is only `atmos://side-chat/{context_id}`.

**Pros**: Compact and directly matches the requested protocol.
**Cons**: Harder to reuse selected text as normal AI Input context. Deleting side mode also deletes context. The mental model is less composable.
**Unknown**: How to represent `Add as context` without inventing a second token anyway.

### Option C - Keep `/side` text but only when generated by the slash menu

Continue serializing the chip as `/side`, but try to distinguish DOM chip nodes from typed or pasted `/side` text.

**Pros**: Smaller code diff.
**Cons**: The serialized text remains ambiguous, tests are brittle, and future prompt processing still sees `/side` as a magic string.
**Unknown**: Whether all paste, restore, and attachment paths can reliably preserve chip node identity.

## Key forks in the road

- **Selection token**: separate `atmos://terminal-selection/{context_id}` token vs. only `atmos://side-chat/{context_id}` - decide in TECH.
- **Side activation**: raw `/side` text vs. protocol chip only - decide in PRD.
- **Side context source**: selected range only vs. selected range plus bounded pane capture - resolved after PRD feedback: side chats keep APP-030 bounded pane capture and append the selected range as explicit user-selected context.
- **Persistence**: client-only composer context vs. backend persisted selection records - decide in TECH.
- **Toolbar anchor**: exact selection rectangle vs. last selection pointer position - decide in TECH based on xterm.js capabilities.

## Ready to promote

- Promote to PRD: option A is the preferred model because context and side mode are separate user intents.
- Promote to PRD: raw `/side` inside typed, pasted, or resolved prompt text must not activate side chat.
- Promote to PRD: `Side chat for selection` must still include APP-030 side chat context capture, then append the user-selected terminal context.
- Promote to TECH: use protocol tokens for side-chat command chips, with `atmos://side-chat/{context_id}` as the command token.
- Promote to TECH: keep terminal selection context client-local unless later requirements need reload persistence.
